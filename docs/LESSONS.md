# Lessons

สิ่งที่ได้เรียนรู้และข้อบกพร่องจาก prototype stage 1 (`offline-v0`) และ stage 2 (`doubles-v2`) ผลและตัวเลขของแต่ละ stage อยู่ใน [PROGRESS.md](PROGRESS.md)

## สรุป 8 ข้อ

1. **ตำแหน่งกล้องสำคัญกว่าโมเดล** ปัญหาส่วนใหญ่ (คนบัง, ฝั่งไกลตัวเล็ก, คนเสิร์ฟนอกเฟรม, ลูกซ้อนกับคนดูข้างสนาม) แก้ได้ด้วยกล้องสูง 2.5–3 ม. ตั้งบนขาตั้ง
2. **ตามลูกด้วยจุดสว่างใช้ได้แค่ฝั่งใกล้** ฝั่งไกลต้องมีโมเดลตามลูก (TrackNet) ไม่อย่างนั้นช็อตเกินครึ่งต้องใส่เอง
3. **คาลิเบรตจากเส้นคอร์ทอัตโนมัติได้** และแม่นกว่าการคลิก 4 มุม
4. **แยกฝั่งจากเส้นเน็ตก่อน แล้วค่อยแยกคนในฝั่ง** ทำให้ประเภทคู่ง่ายลงมาก
5. **ห้ามให้ homography มีอิสระมากเกินข้อมูล** ถ้าเส้นข้างหลุดเฟรม การ refine 8 ตัวแปรจะลอย ต้องลดเหลือ 4 ตัวแปรและใช้แค่จุดที่อยู่ในเฟรม
6. **ความเร็วลูกจาก D/T ไม่พอ** ต้องใช้ตำแหน่งลูกหลายจุดหลังตี
7. **ต้องดูภาพตรวจด้วยตาทุกครั้ง** รายงานตรวจที่สร้างอัตโนมัติจับข้อผิดพลาดที่ตัวเลขสรุปไม่บอก
8. **งาน offline ใช้ข้อมูลจากอนาคตเยอะ** (เทียบเฟรม ±10, smoothing ±45 เฟรม, DP ทั้งแรลลี่) ระบบเรียลไทม์ต้องออกแบบใหม่ให้ใช้แค่อดีตหรือหน่วงสั้นๆ

## 1. กล้องและการถ่าย

**ได้เรียนรู้**
- มือถือวางต่ำหลังคอร์ทให้ภาพฝั่งใกล้ดีมาก แต่ฝั่งไกล 1 พิกเซลราว 8 ซม.
- คลิปแนวตั้ง 540×960 เห็นคอร์ทครบกว่าคลิปแนวนอน แต่ความละเอียดฝั่งไกลต่ำ
- กล้องมือถือที่ "ตั้งไว้เฉยๆ" ก็ยังขยับ ต้องชดเชยทุกเฟรม (stage 2)

**ข้อบกพร่อง**
- stage 1: ปลายคอร์ทฝั่งใกล้ราว 0.9 ม. อยู่นอกเฟรม และฝั่งเราบังฝั่งไกลบ่อย (ภูสิทตามได้ 61%)
- stage 2: คนเสิร์ฟถูกบังหรืออยู่นอกเฟรม 3 ครั้ง (35.76, 71.38, 98.38 วิ) ระบบเดาว่าใครเสิร์ฟ

## 2. คาลิเบรตคอร์ท

**ได้เรียนรู้**
- จุดตัดเส้นหลายจุด (≥8) แม่นกว่า 4 มุม และใช้ได้แม้มุมคอร์ทบางมุมหลุดเฟรม (stage 1: 10 จุด คลาดเคลื่อน ≤6 ซม.)
- คาลิเบรตอัตโนมัติจากเฟรมแรกทำได้ (stage 2):
  1. Hough หาเส้น
  2. หาจุดลู่ของเส้นแนวยาวด้วย RANSAC
  3. เส้นแนวขวางสองเส้นล่างสุดคือเส้นหลัง (0 ม.) กับเส้นเสิร์ฟยาว (0.76 ม.)
  4. จับคู่เส้นแนวยาวกับตำแหน่งจริงด้วย cross-ratio
  5. คำนวณ homography แล้ว refine ด้วย distance transform
- หาคอร์ททุกเฟรมเมื่อกล้องขยับ:
  - เริ่มจากค่าทำนายตามการขยับของเพดานและผนัง
  - ดึงเข้าหาเส้นขาวจริงแบบ 4 ตัวแปร (similarity)
  - คาลิเบรตใหม่ทุก 2 เฟรม แล้วเลือกผลที่เส้นทับสีขาวมากกว่า
  - ทิ้งผลที่ต่างจากค่าทำนายเกิน 8 px
  - ผล: ทับเส้นจริงค่ากลาง 94% และเส้นกระโดดระหว่างเฟรมไม่เกินราว 8 px

**ข้อบกพร่อง**
- refine แบบ 8 ตัวแปรเต็มเคยลอยออกนอกเฟรมเมื่อเส้นข้างหลุดเฟรม แก้แล้วด้วย similarity + จุดอ้างอิงในเฟรม
- `tasks/T04` ยังกำหนดให้คลิก 4 มุม ควรเปิด PR เสนอเปลี่ยนเป็นคาลิเบรตอัตโนมัติแล้วให้คนลากแก้

## 3. ตรวจจับและตามผู้เล่น

**ได้เรียนรู้**
- ใช้ตำแหน่งข้อเท้า (pose) หรือขอบล่างกล่องเป็นตำแหน่งบนพื้น
- ครอปเฉพาะส่วนคอร์ทแล้วรันที่ imgsz 832 ได้ความละเอียดต่อพิกเซลเท่าภาพเต็มที่ 1280 แต่เร็วกว่า
- ฝั่งไกลที่ถูกบังหรือตัวเล็ก ต้องสแกนซ้ำแบบครอปขยาย และลด confidence (stage 1 ใช้ 0.15)
- เท้าฝั่งไกลที่ถูกบังต้องประมาณจากความสูงกล่อง

**ข้อบกพร่อง**
- ตามได้ไม่ครบ: stage 1 ต่ำสุด 61%, stage 2 ต่ำสุด 76% (ฝั่งไกลทั้งคู่)
- ช่วงที่ถูกบังไม่นับระยะวิ่ง ระยะของคนฝั่งไกลจึงต่ำกว่าจริง
- ตำแหน่งฝั่งไกลแกว่ง ความเร็วสูงสุดของบางคนน่าจะสูงเกินจริง (เป้ 5.5 ม./วิ)

## 4. แยกตัวตน (ใครเป็นใคร)

**ได้เรียนรู้**
- กำหนดฝั่งจากเส้นเน็ตทุกเฟรมก่อน แล้วแยกสองคนในฝั่งด้วยลักษณะภายนอก + ความต่อเนื่องของตำแหน่ง (Hungarian)
- ลักษณะที่ใช้ได้จริง:
  - stage 1: ลายพิมพ์บนเสื้อ, ความขาวของรองเท้า
  - stage 2: สีเสื้อช่วงอก
- ต้องหาค่ากลางของลักษณะตลอด track (±45 เฟรม) ค่าต่อเฟรมแกว่งเกินไป

**ข้อบกพร่อง**
- k-means สีเสื้อตรงๆ ใช้ไม่ได้ (stage 1)
- พื้นคอร์ทสีน้ำเงินปนเข้ามาในสีเสื้อ ทำให้ตัวตนสลับช่วง 53–55 วิ (stage 2) แก้แล้วด้วยการตัดสีพื้นออก
- ทั้งหมดขึ้นกับชุดที่ต่างกันชัด ถ้าใส่ชุดคล้ายกันต้องใช้ re-ID model หรือให้ operator สลับ ID (T09)

## 5. ตามลูก

**ได้เรียนรู้**
- ไม่มีโมเดลก็ตามลูกฝั่งใกล้ได้:
  1. หาจุดสว่างเล็กที่สว่างกว่าเฟรม ±3 และ ±10
  2. ชดเชยกล้องแยกระนาบ: ฉากหลังเหนือเส้นหลังฝั่งไกลใช้ homography ของผนัง ส่วนบนคอร์ทใช้ homography ของพื้น
  3. ต่อจุดเป็นเส้นทางสั้นๆ แล้วเลือกเส้นทางทั้งแรลลี่ด้วย DP
  4. ให้เปลี่ยนทิศได้เฉพาะในเขตเอื้อมไม้ของผู้เล่น (คิดตามความสูงกล่อง)
- ตัวกรองที่จำเป็น:
  - ตัดจุดในกล่องคนและรอบรองเท้า (ไม่อย่างนั้นได้เส้นทางปลอมบนตัวคน)
  - เส้นทางต้องยาวพอ (≥60 px) เพื่อตัดลูกที่คนถืออยู่
  - ตัดจุดที่ไม่ขยับ
  - จุดต่อระหว่างเส้นทางต้องห่างไม่เกิน min(30 + 50·gap, 180) px

**ข้อบกพร่อง**
- **ฝั่งไกลตามไม่ได้** ลูกเล็กมากและไปซ้อนกับคนนั่งข้างสนาม แรลลี่ 4, 6, 7, 8 จึงต้องใส่ช็อตเองทั้งหมด
- stage 1 ไม่มีการตามลูกเลย
- เครื่องที่ใช้ทำ prototype โหลดไฟล์โมเดล TrackNetV3 ไม่ได้ (Google Drive และ Hugging Face ถูกบล็อก ส่วนไฟล์ใน repo jiazimo เสีย) ตอนนี้ได้ checkpoint ทางการบนเครื่องของเจ้าของแล้ว (PR #6, #9) แต่ยังไม่ได้ลองกับคลิป stage 2

## 6. ช็อตและแรลลี่

**ได้เรียนรู้**
- เสียงตีช่วง 2–8 kHz ในสนามในร่มชัดพอ ใช้ยืนยันช็อต และใช้แทนลูกตอนมองไม่เห็นได้
- บังคับให้ช็อตสลับฝั่งด้วย DP ลดช็อตเกินและช็อตหายได้มาก
- คนตีคือคนในทีมที่อยู่ใกล้ลูกที่สุด
- แรลลี่ = ช่วงที่มีเส้นทางลูก รวมช่วงที่ห่างกันไม่ถึง 1.8 วิ
- ไฟล์ `config.json` (เพิ่ม/ลบช็อต, เวลาจบแรลลี่, ช่วงที่ไม่นับ) ทำให้แก้ผลเร็ว ระบบจริงควรมีเครื่องมือแบบเดียวกันในหน้า operator

**ข้อบกพร่อง**
- stage 1 นับช็อตได้แค่ 3–8 ช็อตต่อแรลลี่ เพราะช็อตเบาและฝั่งไกลไม่มีเสียงชัด
- stage 2 อัตโนมัติได้ 19 จาก 45 ช็อต ที่เหลือใส่เอง
- จุดที่ยังไม่แน่ใจ:
  - 13.75 วิ: เป้ตีตอนถูกเทมป์บัง
  - 35.76, 71.38, 98.38 วิ: คนเสิร์ฟถูกบังหรือนอกเฟรม
  - 51.47, 61.53 วิ: ช็อตสุดท้ายของแรลลี่ ไม่แน่ใจว่าติดเน็ตหรือข้าม

## 7. ความเร็วลูก

**ได้เรียนรู้**
- สูตรคิดแรงต้านอากาศ: v0 = (e^(kD) − 1) / (kT), k = g / 6.8² (6.8 ม./วิ คือความเร็วปลายของลูกขนไก่)
  - D = ระยะบนพื้นจากคนตีถึงคนที่ตีกลับ
  - T = เวลาระหว่างสองช็อต
- ต้องติดป้าย "EST." ทุกครั้งตาม G4

**ข้อบกพร่อง**
- T สั้นผิดปกติ (0.30 วิ ที่ 98.38 และ 103.0 วิ) ให้ค่าสูงเกินจริง เช่น 325 km/h
- ลูกโด่งได้ค่าต่ำเกินจริง (27–46 km/h) เพราะ D คิดแค่ระยะบนพื้น ไม่รวมความสูง
- ช็อตสุดท้ายของแรลลี่ และช็อตที่ D < 3 ม. หรือลูกอยู่ใกล้เน็ต ไม่มีค่า
- ทางแก้: ใช้ตำแหน่งลูกหลายจุดในช่วง 0.1–0.2 วิแรกหลังตี (ต้องมี TrackNet) หรือใช้สองกล้อง

## 8. สถิติผู้เล่น

**ได้เรียนรู้**
- ระยะวิ่งและความเร็วต้อง smoothing ตามระยะห่างจากกล้อง ฝั่งไกลต้องหนักกว่า

**ข้อบกพร่อง**
- **"พลังกาย" เป็นค่าที่คำนวณขึ้นมา ไม่ได้วัดจริง** (ลดตามความเร็ว ฟื้นตอนยืนนิ่ง) เป็น non-goal ใน GOALS ตอนนี้ v3 เอาออกแล้ว แต่ v2 และ `players.json` ยังมีอยู่
- ระยะวิ่งฝั่งไกลขาดช่วงที่ถูกบัง

## 9. HUD และการเรนเดอร์

**ได้เรียนรู้**
- Pillow ต้องมี RAQM ถึงจะวางสระและวรรณยุกต์ไทยถูก ฟอนต์ที่ใช้คือ IBM Plex Sans Thai + Barlow Condensed
- ส่งเฟรมเข้า ffmpeg ผ่าน rawvideo pipe แล้วใส่เสียงเดิมกลับ ไม่ต้องเขียนไฟล์ภาพทีละเฟรม
- แนวตั้ง: วางสถิติไว้นอกวิดีโอ (v3) อ่านง่ายกว่าแผงซ้อนบนวิดีโอ (v2)
- ป้ายต้องมีตำแหน่งสำรองหลายจุดเพื่อไม่ให้ทับกัน และ LOCK ON ต้องอยู่ในกรอบวิดีโอเท่านั้น
- ทำ preview เฟรมเดียว (`HUD_PREVIEW`) ก่อนเรนเดอร์ทั้งคลิปช่วยประหยัดเวลามาก

**ข้อบกพร่อง**
- HUD ทำด้วย Pillow หลังถ่าย ระบบจริงต้องเป็น HTML overlay ใน OBS (T05)
- mockup ใน `design/mockup-v0/` ใช้ข้อมูลจำลอง ยังไม่ได้ต่อกับข้อมูลจริง

## 10. ความเร็วและการไปสู่เรียลไทม์

**ได้เรียนรู้**
- บน CPU: YOLO11s-pose ที่ 960 ราว 0.4 วิ/เฟรม (stage 1), YOLO11m ราว 1.5–2 วิ/เฟรม (stage 2)
- G1 ต้องการ 60 fps (16.7 มิลลิวินาที/เฟรม) ห่างกันราว 100 เท่า ต้องใช้ GPU + TensorRT และโมเดลเล็กลง (T11)
- งบ latency ใน G1 (p50 ≤150 มิลลิวินาที) เท่ากับ 9 เฟรมที่ 60 fps รวมเวลาประมวลผลแล้ว จึงหน่วงเพื่อ smoothing ได้ไม่กี่เฟรม ไม่พอสำหรับวิธี offline ที่ใช้ ±10 ถึง ±45 เฟรม หรือ DP ทั้งแรลลี่

**ข้อบกพร่อง**
- ยังไม่มีส่วนไหนรันแบบเรียลไทม์
- โค้ด prototype ไม่ตาม `AGENTS.md` และ `CONTRACTS.md`: ไม่มี type hints, ค่าตั้ง hardcode, อ่านเขียนไฟล์ในลูป, ไม่มี test

## 11. วิธีทำงานและเครื่องมือ

**ได้เรียนรู้**
- รายงานตรวจที่สร้างอัตโนมัติช่วยมาก:
  - เส้นคอร์ท 8 เฟรม
  - ภาพทุกช็อต ณ จังหวะตีและ +0.2 วิ
  - ช่วงในแรลลี่ที่ไม่มีช็อตเกิน 2.4 วิ
  - คำเตือนความเร็ว >250 หรือ <25 km/h และช่วงห่างช็อต <0.33 หรือ >2.4 วิ
- ข้อผิดพลาดที่จับได้จากการดูภาพเท่านั้น: ตัวตนสลับ, เส้นคอร์ทลอย, เส้นทางลูกปลอมบนตัวคน, ช็อตผิดในแรลลี่ 4/6/7/8, ป้ายทับกัน
- เครื่องมือในเครื่องที่ใช้ทำงาน:
  - proxy บล็อก download.pytorch.org (ใช้ torch จาก PyPI แทนได้), Hugging Face และ Google Drive
  - `gh` แบบ GraphQL ใช้ไม่ได้ ต้องใช้ REST (`gh api`)
  - สร้าง Release, push tag และ Git LFS ไม่ได้ วิดีโอจึงเก็บใน branch `media` และแบ่งไฟล์ที่เกิน 100 MB

**ข้อบกพร่อง**
- เคยแก้โค้ดด้วยสคริปต์แล้วบรรทัดไปรวมกับคอมเมนต์จนเกิด NameError ถ้ารัน `ruff check` จะจับได้ก่อน
